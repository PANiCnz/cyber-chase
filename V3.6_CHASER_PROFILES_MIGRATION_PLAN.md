# Cyber Chase V3.6 Chaser Profiles Migration Plan

## Purpose

Introduce data-driven Chaser Profiles without rewriting the application or
breaking the current V3.5 match, question, scoring, timer, presenter, intro, or
audience-display flows.

This plan treats the current behavior documented in `PROJECT_CONTEXT.md` and
`HANDOFF.md` as the compatibility baseline. The recently repaired
`questionService.createMatchQuestions()` contract is explicitly protected.

## Repository Review Summary

The repository is a small Express and Socket.IO application with:

- Four static screens: setup, intro, presenter, and display.
- A process-local singleton match in `matchService`.
- Separate contestant and chaser CSV question banks.
- HTTP APIs for match state, questions, answers, and timer controls.
- Socket.IO invalidation events that tell displays to refetch HTTP state.
- An empty `data/chasers.json`, which is the natural starting point for V3.6.

All JavaScript files pass `node --check`. A direct service smoke test confirms
that a match can start, both question banks load, a correct answer increments
the score, and the turn advances.

There is no automated test suite, package lock, committed baseline, or runtime
dependency installation in the reviewed workspace.

## Existing Behavior That Must Be Preserved

1. `POST /api/match/start-match` starts a match.
2. `GET /api/match/state` returns the active match or `null`.
3. Contestant and chaser questions remain separate and randomized.
4. `questionService.createMatchQuestions()` continues to return:
   - `contestantQuestions`
   - `chaserQuestions`
5. The match state retains these existing fields:
   - `contestant.name`, `contestant.department`, `contestant.score`
   - `chaser.name`, `chaser.department`, `chaser.score`
   - `currentPlayer`, question arrays and indexes, and `winner`
6. `GET /api/question/current`, `GET /api/question/upcoming`,
   `GET /api/question/answer`, and `POST /api/question/respond` remain
   compatible.
7. Presenter answer buttons and A/B/C/D keyboard controls keep working.
8. Display score bars, turn state, questions, winner screen, polling, and
   Socket.IO refresh behavior keep working.
9. Existing clients that submit only `chaserName` remain supported during the
   V3.6 migration.
10. Docker deployment continues to use port 3000 and the existing mounted
    `questions`, `data`, and `config` directories.

## Technical Debt Register

### Priority 0: Baseline and Regression Safety

- There are no tests for the working match path called out in `HANDOFF.md`.
- The repository has no commits, so there is no recoverable V3.5 baseline.
- `package.json`, `/health`, and project documentation report different
  versions.
- There is no `package-lock.json`; Docker uses `npm install`, so builds are not
  reproducible.

Action before feature work:

- Create a V3.5 baseline commit or tag.
- Add focused contract tests around question loading, match creation, answer
  processing, and existing API response shapes.
- Align version reporting in one source of truth.
- Generate and commit a lockfile, then use `npm ci` in Docker.

### Priority 1: Match and API Correctness

- `matchRoutes` discards `contestantDepartment` even though setup sends it and
  `matchService.startMatch()` supports it.
- Request bodies are not validated. A missing or non-string `answer` can make
  `processAnswer()` throw while calling `toLowerCase()`.
- Match start accepts empty names and arbitrary chaser names.
- The game requires five points but allocates only five questions per player.
  If either player answers incorrectly, both banks can be exhausted without a
  winner or completion state.
- `GET /api/question/answer` exposes the correct answer to any client. This is
  currently used by the presenter, so it cannot be removed in V3.6 without an
  authorization design.
- HTTP handlers do not consistently distinguish invalid input, no active
  match, exhausted questions, and internal errors.

V3.6 scope:

- Fix department forwarding and add non-breaking validation.
- Record question exhaustion as known debt unless a completion rule is agreed
  and regression-tested separately.
- Preserve the answer endpoint for compatibility; do not combine access-control
  redesign with Chaser Profiles.

### Priority 1: Chaser Data Ownership

- Chaser names are hardcoded in `setup.html`.
- Chaser department is hardcoded in `matchService`, `intro.html`, and
  `intro.js`.
- `data/chasers.json` is empty and has no schema, loader, validation, or API.
- Matches store only a mutable display name, with no stable chaser identifier.
- Future profile edits could change the meaning of historical or active match
  state unless the selected profile is snapshotted.

V3.6 action:

- Make `data/chasers.json` the canonical catalog.
- Select chasers by stable ID.
- Copy the selected public profile fields into match state at match start.
- Continue accepting and returning legacy name and department fields.

### Priority 2: Realtime and Timer Integration Drift

- Socket.IO sends only a timestamp; clients then refetch over HTTP.
- Display also polls every two seconds, creating duplicate update paths.
- Timer state is process-local and polled separately.
- `timer-display.js` is not loaded by `display.html`.
- `timer-presenter.js` is not loaded by `presenter.html`, and the referenced
  timer controls do not exist.
- `presenter-realtime-patch.js` and `server-socket-snippet.js` are upgrade
  artifacts that duplicate active logic but are not loaded.

V3.6 action:

- Keep the current invalidation-plus-refetch model to limit feature risk.
- Emit one refresh after a successful match start if screens need immediate
  profile updates.
- Inventory and label dormant patch files; remove them only in a separate,
  tested cleanup change.
- Repair timer integration separately from profile work.

### Priority 2: Data Parsing and Runtime State

- CSV parsing uses `split(",")`, so quoted commas, embedded quotes, CRLF edge
  cases, and malformed rows are not handled.
- Question files are synchronously read using `process.cwd()`, coupling startup
  to the launch directory.
- Question pools, match state, and timer state are module globals.
- One server process supports only one match, and restart loses all state.
- Multiple Node workers or replicas would each have different state.

V3.6 action:

- Do not replace the state model during the profile feature.
- Isolate chaser catalog loading behind a service so storage can change later.
- Resolve data paths from the application root and fail startup clearly when
  profile data is invalid.
- Schedule persistence and multi-match support for a later architecture
  milestone.

### Priority 2: Browser Safety and Maintainability

- Browser scripts rely on element IDs becoming global variables.
- User and data-derived values are inserted with `innerHTML` in places,
  including the winner name and answer choices.
- Fetch calls generally have no network, non-JSON, or error-state handling.
- Presenter CSS contains selectors for controls and panels absent from the
  current HTML, indicating milestone drift.
- Styling and scripts are page-specific but have no shared utilities or
  accessibility conventions.

V3.6 action:

- Use explicit `getElementById` references in touched profile code.
- Render profile text with `textContent`; do not inject profile strings into
  HTML templates.
- Add visible loading, empty-catalog, and failed-load states to setup.
- Avoid broad frontend refactoring outside files needed for profiles.

### Priority 3: Operations and Documentation

- Health checks report only a static status and stale version.
- Docker uses a floating Node 22 image and installs dependencies at build time
  without a lockfile.
- There is no `.dockerignore`, test command, lint command, or CI configuration.
- `README.md`, `README.txt`, `INSTALL.md`, and `INSTALL.txt` describe different
  milestone fragments rather than one current deployment guide.
- The empty `config` directory is mounted but has no documented contract.

V3.6 action:

- Add catalog readiness to health diagnostics without exposing profile data.
- Consolidate current V3.6 setup and data-maintenance instructions.
- Keep operational hardening changes small and independently reversible.

## Proposed V3.6 Profile Contract

### Canonical Catalog

Use `data/chasers.json` as an array:

```json
[
  {
    "id": "rob",
    "name": "Rob",
    "title": "The Firewall",
    "department": "Information Security",
    "bio": "Short presenter-approved profile text.",
    "active": true,
    "theme": {
      "accentColor": "#ff4d4f"
    }
  }
]
```

Rules:

- `id` is required, unique, lowercase, and stable.
- `name` and `department` are required non-empty strings.
- `title`, `bio`, and `theme` are optional.
- `active` defaults to `true`.
- Photo fields may be reserved later, but V3.6 must not require an image
  because Chaser Photos is a separate planned feature.
- Unknown fields should be ignored by public serializers so internal metadata
  is not leaked accidentally.

### Service Boundary

Add `src/services/chaserService.js` with a narrow API:

- `loadChasers()`
- `listActiveChasers()`
- `getChaserById(id)`
- `findChaserByName(name)` for legacy requests
- `createMatchSnapshot(chaser)` to whitelist match-safe fields

The service owns file loading, schema validation, normalization, and public
serialization. Routes and `matchService` must not read JSON directly.

### HTTP API

Add:

- `GET /api/chasers` returns active public profile summaries.
- `GET /api/chasers/:id` returns one active public profile or 404.

Extend, but do not replace:

```json
POST /api/match/start-match
{
  "contestantName": "Alex",
  "contestantDepartment": "Finance",
  "chaserId": "rob",
  "chaserName": "Rob"
}
```

Resolution order:

1. Use `chaserId` when present.
2. Otherwise resolve the legacy `chaserName`.
3. Return 400 for missing selection and 404 for an unknown or inactive chaser.

During migration, the setup page should send both `chaserId` and `chaserName`
so an old server or old client remains understandable.

### Match-State Compatibility

The selected profile is snapshotted into the existing chaser object:

```json
{
  "chaser": {
    "id": "rob",
    "name": "Rob",
    "title": "The Firewall",
    "department": "Information Security",
    "bio": "Short presenter-approved profile text.",
    "theme": {
      "accentColor": "#ff4d4f"
    },
    "score": 0
  }
}
```

Existing consumers continue to read `chaser.name`, `chaser.department`, and
`chaser.score`. New fields are additive. Active matches do not change if the
catalog file is edited after match start.

## Phased Migration

### Phase 0: Freeze the V3.5 Baseline

1. Commit the reviewed working tree as the V3.5 baseline.
2. Add a test script using Node's built-in test runner to avoid a framework
   migration.
3. Capture tests for current service and route contracts.
4. Add a smoke checklist for setup, intro, presenter, display, timer API, and
   Docker startup.
5. Align version metadata and create a lockfile.

Exit criteria:

- The current match smoke path passes locally and in Docker.
- A failed migration can be reverted to one known commit.

### Phase 1: Add the Catalog Behind the Current UI

1. Populate `data/chasers.json` with the four current names.
2. Add `chaserService` and schema validation.
3. Add catalog unit tests for valid, duplicate, missing, inactive, and malformed
   records.
4. Add chaser routes and register them in `server.js`.
5. Do not change match creation or frontend behavior yet.

Exit criteria:

- `/api/chasers` returns the current four selectable chasers.
- Existing match APIs and pages are unchanged.
- Invalid catalog data fails clearly rather than silently producing bad state.

### Phase 2: Make Match Creation Profile-Aware

1. Extend `startMatch` to accept a resolved chaser snapshot while preserving a
   compatibility wrapper for the old name-based signature.
2. Update `matchRoutes` to forward `contestantDepartment`.
3. Resolve `chaserId` first and legacy `chaserName` second.
4. Add profile fields to `match.chaser` without removing existing fields.
5. Add request validation and stable 400/404 responses.

Exit criteria:

- Old name-only requests still start a match.
- New ID-based requests start the same match with additive profile fields.
- Question selection, scoring, turns, and winner behavior are unchanged.

### Phase 3: Migrate Setup to the Catalog

1. Replace hardcoded options with data loaded from `/api/chasers`.
2. Preserve the existing select control and start-button workflow.
3. Show title, department, and bio for the current selection.
4. Use safe text rendering and explicit element references.
5. Disable match start while loading and show actionable load/empty/error
   states.
6. Keep a small static fallback list for one release only if offline startup is
   an operational requirement; otherwise fail visibly.

Exit criteria:

- The same four chasers are selectable.
- The request sends both stable ID and legacy name.
- Setup still redirects to `intro.html` after a successful start.

### Phase 4: Add Profile Presentation Incrementally

1. Intro: display optional title and bio while preserving name and department.
2. Presenter: add a compact chaser profile panel without moving answer controls.
3. Display: add title or theme accents without changing score, turn, question,
   timer, or winner element IDs.
4. Apply profile accent colors through validated CSS custom properties.
5. Provide defaults when optional fields are absent.

Exit criteria:

- Old match state without new fields renders exactly as before.
- New profile fields enhance all relevant screens.
- No screen depends on photos.

### Phase 5: Integration, Deployment, and Cleanup

1. Run service, API, browser, and Docker smoke tests.
2. Verify a legacy request and a new profile request.
3. Verify active-match snapshot behavior after catalog edits.
4. Verify malformed catalog startup behavior.
5. Document profile editing and deployment.
6. Mark duplicate patch files as deprecated; remove only after confirming they
   are not part of any deployment package.
7. Release as V3.6 with a rollback to the V3.5 baseline image or commit.

## Required Test Matrix

### Service Tests

- Loads the current four profiles.
- Rejects duplicate IDs and missing required fields.
- Filters inactive profiles from public lists.
- Resolves IDs and legacy names case-insensitively where appropriate.
- Creates a whitelisted immutable match snapshot.
- Preserves `createMatchQuestions()` output and five-question selection.
- Preserves score increment and turn advancement.
- Handles missing answers without throwing.

### API Tests

- Lists profiles and returns one profile.
- Returns 404 for unknown or inactive IDs.
- Starts a match with `chaserId`.
- Starts a match with legacy `chaserName`.
- Preserves contestant department.
- Returns stable errors for invalid bodies and no active match.
- Preserves all existing endpoint response fields.

### Browser Smoke Tests

- Setup loads profiles, changes preview, and starts a match.
- Intro shows contestant and selected chaser data, then redirects.
- Presenter loads the current question and submits A/B/C/D by click and key.
- Display updates names, scores, turn, questions, and winner.
- Socket refresh and polling still converge on the same state.
- Missing optional profile fields render sensible defaults.
- Profile text containing HTML-like characters is displayed as text.

### Docker Smoke Tests

- Clean image builds reproducibly.
- `/health`, `/api/chasers`, and static pages respond.
- Mounted `data/chasers.json` is loaded.
- Invalid mounted data produces a clear health/startup failure.
- Restart behavior remains documented as process-local and non-persistent.

## Rollout and Rollback

- Keep each phase in a separate commit.
- Deploy catalog API before switching setup to consume it.
- Treat all match-state additions as optional on the frontend.
- Keep legacy `chaserName` support for at least V3.6.
- Do not change scoring completion rules, realtime architecture, timer
  architecture, or persistence in the profile release.
- Roll back by reverting the latest phase or redeploying the V3.5 baseline;
  the question CSVs and existing API shapes remain compatible.

## Definition of Done

V3.6 is complete when:

- Chasers are managed in one validated data catalog.
- Setup no longer owns the chaser list.
- Matches use stable chaser IDs and snapshot public profile data.
- Existing name, department, score, question, answer, timer, Socket.IO, and
  display behavior remains functional.
- Legacy name-based match start still works.
- Automated regression tests cover the protected V3.5 match path.
- Browser and Docker smoke tests pass.
- Profile maintenance and rollback are documented.

## Explicitly Deferred

To keep V3.6 low-risk, defer these items:

- Chaser photo asset management.
- Authentication or presenter authorization.
- Multi-match and multi-room support.
- Database persistence and historical statistics.
- Leaderboards and dashboard work.
- Replacing HTTP polling with full Socket.IO state replication.
- Redesigning match completion or scoring rules.
- Broad UI, CSS, or module-system rewrites.
